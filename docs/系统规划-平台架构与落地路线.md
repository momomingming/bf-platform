> 范围：对现有 bf-platform 做系统级梳理与重规划，明确"先把系统写好"（暂不急着上线）的工作边界

## 0. 一句话现状与本规划目标

现状：平台的 **ML 预测引擎（modeling.py）已成型**，八标签页的 Streamlit 界面（数据分析/预测/对比/自定义 + 导入/计算）已搭好；
**数据层（schema / importer / metrics / db / panels）2026-09-13 已写出并接到界面，但只躺在本地 D 盘、未提交、未推送、未部署**。
代码层面最关键的链路——"导入数据 → `to_model_frame()` 中英文字段翻译 → 喂给 modeling 训练"——在设计上是**对齐且正确**的（`schema.py` 内嵌了 `LIQUID_MODEL_FEATURES/TARGETS` 与 `modeling.py` 成对一致），不是断裂，只是两份拷贝未来可能不同步。

本规划目标：**把它从"能跑的 demo"升级为"可追溯、可复现、真实数据能真正驱动预测"的竞赛级平台**，并给出分阶段落地路线。C 原则：先写对、写稳，再上线。

## 1. 平台定位与边界

### 1.1 当前定位 vs 竞赛定位的错位（需先拍板）
- 代码命名：**"锂硫电池隔膜填料与基底材料设计平台"**（液态/固态通用）。
- 竞赛作品：**"低成本玄武岩纤维（BF）构筑高稳定锂硫电池固态电解质"**。
- 错位：竞赛核心是**固态电解质 + 玄武岩纤维填料**，而当前平台大半是液态隔膜填料体系。建议二选一或兼得：
  - A. 平台改名 + 增加"玄武岩纤维固态电解质"为**一等公民场景**（推荐，契合竞赛）；
  - B. 保留通用平台，竞赛时用"固态体系 + BF 填料"子集做专题演示。

### 1.2 目标用户与场景
| 角色 | 场景 | 平台提供的价值 |
|------|------|----------------|
| 你自己（研发） | 整理文献、导入实验/文献数据、算指标、看预测 | 数据沉淀 + 快速预测 |
| 竞赛评委 | 看演示、验证数据可追溯 | 导入→计算→存储→预测全链路可复现 |
| 同行研究者 | 自定义材料、对比、搜索知识库 | 知识库 + 可解释预测 |

### 1.3 核心价值链
```
文献/实验数据 ──导入(校验/去重)──▶ 结构化样本(库)
        │                                      │
        └──精细化计算(口径/精度/可追溯)──▶ 计算指标(库)
                                                 │
                              ┌──────────────────┴───────────────┐
                         基线模型(合成数据)              真实数据≥阈值→重训/校准
                                                 │
                                          预测引擎 → 对比/排名/推荐
```

## 2. 分层架构（见架构图）

四层 + 外部输入，已在架构图中标注。要点：

- **外部输入**：合成数据 `generate_data`（默认种子/基线）与真实文献数据（Excel/CSV 导入）。

## 3. 三大功能（导入 / 计算 / 库）的落位、现状与补强

### 3.1 文件导入 importer
- **现状**：已实现单流水线 `读取→列映射→校验→去重→落库`，五阶段进度回调，编码/分隔符/表头自动探测，别名归一化，三级校验，`content_hash` 去重，模板下载齐全。
- **关键接口**：`ImportConfig`、`ImportReport`、`import_file()`、`parse_records()`（预览）、`build_template()`。
- **待修（P1）**：
  1. MD5"已导入提示"是死代码——`UploadedFile` 既非路径也非 bytes，需改读 `getvalue()` 字节才能命中 `find_batches_by_md5`。
  2. 汇总行数对账虚高：库内重复（Db）既计"有效"又计"重复"，导致 `总行 ≠ 有效+错误+重复`，需修口径。
  3. `config.header_row` 手动指定时 `total_rows` 仍用自动探测值，显示错。
- **待补**：导入日志/审计（谁、何时、哪批、来源标签）进 `batches` 表可查；大文件（>20 万行）分块进度。

### 3.2 精细化计算 metrics
- **现状**：`METRIC_SPECS` 单一声明口径（公式/单位/精度/版本），`CalcConfig` 落 JSON 快照 + `params_hash`，每条结果记 `run_id/params_hash/formula_version/inputs_json`，`Decimal` 按精度舍入，改参数→新 `run_id`，旧 run 保留。
- **关键接口**：`CalcConfig`、`run_metrics()`、`compute_frame()`（只算不落库）、`specs_frame()`、`fit_activation_energy()`（≥3 温度点才拟合）。
- **待修（P1）**：
  1. `composite_score` 的 `inputs_json` 漏了 `shuttle_factor` 等来源字段，追溯不全。
  2. `source_tag`（数据来源）只在 `params_json` 里不是列，无法按来源筛选。
- **待补（战略）**：**计算结果是死胡同**——算出的派生指标（如面容量、面比电阻、综合评分）没有回流成 ML 的特征或目标。需打通"计算→建模"闭环（见 §4.4）。

### 3.3 数据库扩充 db + schema
- **现状**：`schema.py` 为字段单一事实源（类型/单位/范围/必填/枚举/体系），`db.py` 做版本化幂等迁移（v1→v2）、WAL、外键级联、7 项一致性自检、`content_hash` UNIQUE 兜底。
- **关键接口**：`init_db()`、`fetch_samples/list_batches/fetch_errors/delete_batch`、`create_metric_run/save_metric_results/fetch_metric_pivot/list_metric_runs`、`verify_consistency()`、`compute_content_hash/compute_params_hash`。
- **待修（P0）**：`BF_DB_PATH` 未设置 → 每次部署 `robocopy` 覆盖 `platform.db`，导入与计算结果**更新一次丢一次**。必须指到包外（如 `C:\apps\data\platform.db`）并写入 nssm 服务环境。
- **待补（增强）**：两份字段拷贝（`schema.LIQUID_MODEL_FEATURES` 与 `modeling.LIQUID_FEATURES`）应改为**单一来源**（见 §4.1）；增加"模型版本表"支撑模型可追溯（见 §4.3）。

## 4. 最关键的设计决策（决定系统能否"写好"）

### 4.1 字段单一事实源（已做对，要消除双份拷贝）—增强项
当前 `schema.py` 与 `modeling.py` 各自维护一份特征/目标列名。设计上对齐，但两份拷贝长期会漂移。
**决策**：以 `schema.py` 为唯一真相，`modeling.py` **导入** `LIQUID_MODEL_FEATURES/TARGETS`（或反之），删除重复定义。任何列名变更只改一处。

### 4.2 真实文献数据如何真正驱动模型（战略核心）
当前逻辑（`app.py` 第 134-149 行）：仅当某体系库内样本 **≥ 30** 才用真实数据替换合成数据训练模型。
**问题**：你刚整理的文献 Excel 仅 18 条；玄武岩纤维固态场景真实样本极少。结果——**平台声称用文献数据，但模型其实一直是合成数据在跑**，竞赛说服力弱。
**决策（三选一，需你拍板）**：
- **方案甲（推荐·稳健）混合/迁移学习**：始终用合成数据作基线预训练，真实数据到达后做**微调/校准**（如 Platt scaling 或特征偏移校正），即使 <30 条也逐步纳入，给出"真实数据覆盖度"指标。
- **方案乙（阈值保留但下调）**：把门槛降到 10~15 条，并对小样本做交叉验证 + 不确定性放大提示。
- **方案丙（纯真实）**：坚持 ≥30 才切，但配套"数据众筹/持续导入"运营，先积累。

### 4.3 模型版本化与可追溯（竞赛硬需求）
当前 `@st.cache_resource` 每次 Streamlit 加载**内存重训**，无模型产物、无版本、不可复现，无法说清"这条预测由哪批数据、哪个参数训出"。
**决策**：新增 `model_runs` 表 + `pickle` 模型产物（或 `joblib`），记录 `model_id / trained_on_batches / sample_count / feature_set_hash / metrics_summary / created_at`。预测结果可回溯到 `model_id`。平台侧边栏展示"当前生效模型：vX（真实数据 N 条 / 合成基线）"。

### 4.4 计算 → 建模反馈闭环（打通死胡同）
`metrics.py` 算出的派生指标（面容量、面比电阻、综合评分、活化能）应回流：
- 作为 **ML 目标**（如"综合评分"作为排序目标）或 **特征**（如"面比电阻"替代部分原始字段）；
- 写入 `metric_results` 后由 `to_model_frame` 一并纳入训练集。
**决策**：在 `schema.py` 增加"派生字段"分区，`metrics` 计算结果落库即成为可建模字段，闭环打通。

### 4.5 部署与数据安全（C 之后才做，但设计现在定）
- `BF_DB_PATH` 指向包外持久路径，写入 nssm 服务环境（Windows 服务 `BFPlatform`）。
- 迁移只能新增不能改旧（`MIGRATIONS` 幂等），部署脚本 `robocopy` 用 `/E` 不用 `/MIR`（保 logs/保库）。
- 单文件 SQLite 备份 = 复制文件；上线前在云上 Python 3.11.9 跑 `tests/` 三个自测 + AppTest 验收。

## 5. 数据流与一致性契约

导入 → 落库 → 计算 → 建模 全链路需满足以下一致性（现有 7 项 + 新增）：
1. 批次行数 = 有效 + 错误 + 库内重复（修 P1-2 后成立）。
2. `content_hash` 唯一，库内不存重复样本。
3. 外键级联：删批次联删其样本与错误。
4. 计算 `run` 的输入 `sample_id` 必须仍存在于 `samples`（孤儿 run 自检）。
5. 每个 metric run 的 `params_hash` 可反查 `CalcConfig` 快照。
6. 模型 `model_id` 可反查 `trained_on_batches` 与 `feature_set_hash`。
7. **新增**：`schema` 字段集变更后，旧 `model_runs` 标记 `stale`，禁止用于新预测。
8. **新增**：导入样本列必须覆盖当前 `LIQUID_MODEL_FEATURES/TARGETS`（否则该体系不能切真实训练，给告警）。
